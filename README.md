# pdf-rag — Гибридный RAG-поиск по документам

Векторный поиск (ChromaDB + bge-m3 через Ollama) + BM25 + FlashRank reranker + фильтр по продукту + **постраничные метаданные**.  
Всё локально, без облаков. LLM для генерации ответа — `qwen3:8b` локально.

## Быстрый старт

```bash
chmod +x setup.sh
./setup.sh            # установка .venv + зависимостей + проверка Ollama
./setup.sh --systemd  # то же + установка systemd-сервиса
```

Перед запуском положи свои PDF, DOCX, PPTX в `data/pdfs/`.

Сервер встанет на порту 11436. После первого запуска проиндексируй документы:

```bash
cd pdf-rag && .venv/bin/python src/ingestion_hybrid.py \
    --product "Название продукта" \
    --summary "Краткое описание"
```

## Поиск

```bash
curl 'http://localhost:11436/search?query=ваш+запрос'
curl 'http://localhost:11436/search?query=запрос&product=Название+продукта'
curl 'http://localhost:11436/search?query=запрос&k=20'
```

Ответ — JSON с массивом `results[]`. Каждый чанк содержит:
- `source` — имя файла
- `text` — фрагмент текста
- `page` — номер страницы в PDF (если есть)
- `product` — продукт
- `rerank_score` — оценка реранжера

## Добавление документов

Через HTTP:
```bash
curl -X POST http://localhost:11436/upload -F "file=@/путь/к/файлу.pdf"
curl -X POST http://localhost:11436/ingest \
  -H "Content-Type: application/json" \
  -d '{"product": "Название", "summary": "Описание"}'
```

## Генерация ответа

RAG-движок возвращает найденные чанки (текст + source + page). Финальный ответ собирает внешняя LLM — по умолчанию `qwen3:8b` локально.

## Подключение к агенту

После развёртывания сервера любой ИИ-агент может искать и добавлять документы через HTTP.

### Настройка агента

Укажи в инструкциях агента адрес сервера и формат запросов:

```
Поиск документов: curl -s "http://<host>:11436/search?query=${запрос}"
Загрузка нового документа: curl -X POST http://<host>:11436/upload -F "file=@путь/к/файлу"
Инкрементальная индексация: curl -X POST http://<host>:11436/ingest \
  -H "Content-Type: application/json" \
  -d '{"product": "Название", "summary": "Описание"}'
```

Ответ поиска — JSON с массивом `results[]`, каждый содержит `source` (имя файла), `page` (номер страницы), `text` (фрагмент), `product`, `rerank_score`. Агент формирует ответ на основе этих чанков.

### Что может агент через сервер

- Искать по всем документам с фильтром по продукту
- Загружать новые PDF/DOCX/PPTX — сервер сам проверяет дубликаты по SHA256
- Запускать индексацию новых документов
- Проверять ответ на соответствие документам (`POST /validate`)
- Получать список файлов и статистику индекса (`GET /files`, `GET /status`)

## Требования к серверу

| Компонент | Минимум | Комфортно |
|-----------|---------|-----------|
| **RAM** | 8 GB | 16+ GB |
| **CPU** | 2 ядра | 4+ ядра |
| **GPU** | Не обязателен (CPU-режим) | NVIDIA с 6+ GB VRAM |
| **SSD** | 50 GB свободно | 200+ GB |
| **Ollama** | Только при индексации | Опционально на runtime |

**Пояснения:**
- **RAM:** search_server держит ChromaDB (векторный индекс) и FlashRank (модель реранжинга) в памяти. При 500 документах достаточно ~1 GB, при 2000+ — до 3 GB. ChromaDB на bge-m3 (1024d) весит ~300 МБ на 23К чанков.
- **GPU:** используется только на этапе генерации эмбеддингов при индексации. На CPU — в 10-30× медленнее (часы вместо минут). На runtime поисковый сервер GPU не требует.
- **SSD:** растёт пропорционально количеству документов. Проект + код ~5 GB, остальное — PDF-файлы и индексная база.
- **Ollama:** эмбеддинги предвычислены при индексации и хранятся в ChromaDB. Для обычной работы Ollama не нужна, включается только при добавлении новых документов.

## Переменные окружения

Все настраиваются через `export` или `.env` — см. INSTRUCTIONS.md.  
Ключевые: `CORS_ORIGINS` (по умолчанию `*`), `RAG_EMBED_MODEL` (по умолчанию `bge-m3:latest`), `RAG_OLLAMA_URL`.

## Технические детали

- Поиск: ChromaDB (n_results=30) + BM25 (n_results=30) → RRF fusion → FlashRank reranker
- Эмбеддинги: **bge-m3:latest** через Ollama, метрика cosine, размерность **1024**
- Чанкование: **768 слов**, overlap 128, постраничная разбивка
- Дедупликация по **SHA256** при загрузке
- Все операции доступны через HTTP — shell не требуется
- В метаданных каждого чанка: `source`, `page` (номер страницы), `chunk` (номер чанка на странице), `product`, `summary`

### Модель эмбеддингов

По умолчанию используется `bge-m3:latest` (BAAI, 567M параметров, 1024 dim).

**Особенности:**
- **Мультиязычная** — поддерживает 100+ языков (русский, немецкий, французский и т.д.)
- **Требует Ollama** — эмбеддинги генерируются через Ollama
- **Не нужна на runtime** — эмбеддинги предвычислены при индексации. Ollama запускается только при добавлении новых документов.
- **Требует префиксов** для правильной работы: `search_query:` / `search_document:` (реализовано в ingestion и search)
- **1024 dim** — ChromaDB и BM25 pkl-файлы завязаны на эту размерность

**Смена модели эмбеддингов:**
1. Поменять `model_name` в `hybrid_search.py` и `ingestion_hybrid.py`
2. Поменять `collection_name` в ChromaDB (или создать новую коллекцию)
3. Запустить полную переиндексацию — старые вектора несовместимы с новой моделью
4. Обновить `RAG_EMBED_MODEL` в `.env`
5. Перезапустить search_server
